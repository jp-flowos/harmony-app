# 전화번호 인증 기반 가입·로그인 설계

작성일: 2026-07-20
상태: 승인됨 (구현 계획 대기)

## 배경

현재 인증은 이메일+비밀번호 가입과 카카오 OAuth 두 경로다. 이메일 경로를 전화번호 SMS 인증으로 교체한다. 비밀번호는 없애고, 가입과 로그인 모두 전화번호+인증번호로 처리한다.

### 왜 지금 바꾸는가

이메일 경로는 시니어 사용자(55~70세)에게 두 가지 실패 지점을 만들었다.

- 오타 이메일로 가입하면 복구가 불가능하다. 이 프로젝트는 Supabase 이메일 확인이 꺼져 있어 존재하지 않는 주소도 즉시 confirmed 처리되고, 비밀번호 재설정 메일도 오타 주소로 간다. 2026-07-20 실제로 발생했다 (`jangapn1683@naver.com` vs `jangpan1683@naver.com`).
- 비밀번호 자체가 이탈 지점이다. 기억·입력·재설정 모두 비용이다.

전화번호는 오타가 나면 인증번호가 오지 않으므로 **가입 시점에 즉시 드러난다.** 복구 불가능한 계정이 생기지 않는다.

### 현황 (2026-07-20 기준)

| 항목 | 값 |
|---|---|
| auth 사용자 | 9명 (이메일 7, 카카오 2) |
| `auth.users.phone` 보유 | 0명 — Supabase 전화 인증 미사용 |
| `h_profiles.phone` 보유 | 13개 중 1개 |
| 클럽 활동 있는 사용자 | 2명 |
| SMS 공급자 | 미설정 (`phone_provider_disabled`) |

출시 전이고 실사용자가 사실상 없다. 대규모 마이그레이션 문제가 아니다.

| 항목 | 결정 |

## 구현 방식

**Supabase 네이티브 phone auth + Send SMS Hook**을 사용한다.

Supabase가 OTP 생성·검증·세션 발급을 담당하고, 우리는 **발송만** 위임받는다. `signInWithOtp({ phone })` → Supabase가 우리 훅을 호출 → 우리가 SMS 공급자로 전달. `verifyOtp()` 성공 시 Supabase가 세션을 발급한다.

### 왜 이 방식인가

세션 처리가 이번 작업에서 가장 위험한 영역이다. 2026-07-20 하루에만 세션 관련 버그 3건을 고쳤다 (로그아웃 GET 프리페치, 손상 쿠키 500, 홈 라우트 충돌). 네이티브 방식은 **기존 쿠키·proxy·`requireUser()` 코드를 건드리지 않는다.**

대안으로 검토한 것들:

- **자체 OTP 구현**: Supabase가 전화번호용 세션 발급 API를 제공하지 않아, 가짜 이메일(`01012345678@phone.local`)로 매직링크를 우회해야 한다. 이메일을 없애자는 목표와 충돌하고 세션 발급·갱신을 직접 떠안는다.
- **자체 OTP + 자체 JWT**: RLS 연동과 토큰 갱신을 전부 재구현해야 한다. 이 규모에 맞지 않는다.

### 제약

Send SMS Hook은 Supabase 유료 플랜 기능이다. **배포 전 플랜 확인이 필요하다.** 플랜이 맞지 않으면 자체 OTP 방식으로 재설계해야 하며, 그 경우 이 스펙의 서버 구성 절을 다시 쓴다.

## 화면 흐름

가입과 로그인을 하나의 화면으로 합친다. 번호를 입력하기 전에는 신규인지 기존인지 알 수 없고, 시니어 사용자에게 둘 중 고르라고 묻는 것 자체가 이탈 지점이다.

```
/login  ─ [카카오로 시작하기]
        └ 휴대폰 번호 입력 → [인증번호 받기]
              ↓
          인증번호 6자리 입력 → [확인]
              ↓
        신규 ─→ /onboarding ─→ 홈(/)
        기존 ─→ 홈(/)
```

온보딩 단계는 기존 5단계 앞에 약관 동의를 추가해 6단계가 된다.

```
약관동의 → 글씨크기 → 닉네임 → 지역 → 취미 → 사진
```

### 약관 동의를 온보딩 첫 단계에 두는 이유

번호 입력 화면에 두면 기존 사용자에게도 매번 노출되고, 인증 전 동의는 개인정보 수집 동의로서 근거가 약하다. 인증을 마치고 신규로 판정된 사용자에게만 받는 것이 맞다.

부수 효과로 **카카오 가입자의 동의 누락이 함께 해결된다.** 현재 카카오 경로(`/api/auth/callback` → `/onboarding`)는 `h_user_consents`에 아무 기록도 남기지 않는다. 온보딩 첫 단계로 옮기면 두 경로 모두 동의를 남긴다.

### 카카오 계정 분리 안내

카카오는 전화번호를 제공하지 않으므로 카카오 계정과 전화번호 계정을 자동으로 연결할 수 없다. 같은 사람이 두 계정을 갖게 되는 상황을 코드로 막을 방법이 없다.

로그인 화면에 안내 문구를 둔다: **"이전에 카카오로 시작하셨다면 카카오 버튼을 눌러주세요."**

## 서버 구성

### 엔드포인트

| 경로 | 역할 |
|---|---|
| `POST /api/auth/phone/send` | 010 검증 → 정책 검사 → `signInWithOtp()` |
| `POST /api/auth/phone/verify` | 실패 횟수 검사 → `verifyOtp()` → 세션 쿠키 발급 |
| `POST /api/auth/sms-hook` | Supabase가 호출. 서명 검증 후 발송 어댑터로 위임 |

정책 수치는 전부 Supabase 호출 **앞단**에서 강제한다. Supabase 내장 제한은 요구사항(번호당 일 5회, IP당 일 20회, 입력 실패 5회)만큼 세분화되지 않는다.

`/api/auth/sms-hook`은 Supabase가 인증 없이 호출하므로 `src/proxy.ts`의 `publicPaths`에 추가한다. 대신 Supabase가 붙이는 서명 헤더를 시크릿으로 검증한다. **검증 실패 시 401을 반환하고 발송하지 않는다.**

### 발송 어댑터

```ts
// src/lib/sms/types.ts
export interface SmsSender {
  send(to: string, text: string): Promise<void>;
}
```

- `consoleSender` — 개발용. 서버 로그에 수신번호와 인증번호 출력
- 공급자 확정 시 어댑터 파일 하나 추가 (예: `solapiSender`)
- `getSmsSender()`가 `SMS_PROVIDER` 환경변수로 선택

공급자가 바뀌어도 어댑터 외의 코드는 수정하지 않는다.

## 정책 저장

새 테이블을 만들지 않고 기존 `h_auth_attempts`를 사용한다. `find-id`와 `login-hint`가 이미 쓰는 패턴이며, 전화번호는 원문 대신 서버 시크릿 HMAC 키로 넣는다.

| 액션 | 키 | 제한 |
|---|---|---|
| `otp_send` | 클라이언트 IP | 일 20회 |
| `otp_send_target` | HMAC(번호) | 일 5회, 재발송 30초 |
| `otp_fail_target` | HMAC(번호) | 실패 5회 |

- 발송에 성공하면 해당 번호의 `otp_fail_target` 행을 삭제해 실패 카운터를 리셋한다.
- 번호를 바꾸면 HMAC 키가 달라지므로 이전 인증 상태는 자동으로 분리된다. 별도 초기화 로직이 필요 없다.
- 실패 5회에 도달하면 검증을 차단하고 재발송을 요구한다.

## 전화번호 저장 형식

`auth.users.phone`은 Supabase가 E.164(`+821012345678`)로 저장한다. `h_profiles.phone`도 **같은 형식으로 통일한다.**

형식이 두 개면 조회가 어긋나는 버그가 생긴다. 2026-07-20에 고친 로그인 실패 버그가 정확히 그 유형이었다 — 이메일 앞뒤 공백이 정규화되지 않아 정상 계정이 로그인하지 못했다.

기존 데이터는 1건(`01012345678` 형식)뿐이라 마이그레이션 부담이 없다.

변환 헬퍼를 `src/lib/auth-utils.ts`에 추가한다.

| 함수 | 용도 |
|---|---|
| `toE164KR(input)` | `010-1234-5678` → `+821012345678` |
| `formatPhoneDisplay(e164)` | `+821012345678` → `010-1234-5678` |

기존 `normalizePhone`, `isValidPhone`, `formatPhoneInput`은 입력 폼에서 계속 쓴다.

## 오류 메시지

`auth-errors.ts`를 OTP 사유로 재작성한다. 영문 원문이 노출되지 않도록 단일 매핑 지점을 유지하는 기존 구조는 그대로 둔다.

| 사유 | 문구 방향 |
|---|---|
| `invalid_phone` | 휴대폰 번호를 다시 확인해주세요 (010으로 시작하는 번호) |
| `send_limit` | 오늘 받을 수 있는 횟수를 넘었어요. 내일 다시 시도해주세요 |
| `resend_wait` | 잠시 후 다시 받을 수 있어요 (남은 초 표시) |
| `code_mismatch` | 인증번호가 맞지 않아요. 다시 확인해주세요 |
| `code_expired` | 인증번호 유효시간이 지났어요. 다시 받아주세요 |
| `fail_limit` | 여러 번 틀렸어요. 인증번호를 다시 받아주세요 |
| `unknown` | 잠시 후 다시 시도해주세요 |

## 테스트

**단위 테스트 (`bun test`)** — 순수 함수로 분리해 덮는다.
- `toE164KR` / `formatPhoneDisplay` 왕복 변환, 하이픈·공백 처리
- `isValidPhone` 010 검증 (해외 번호 거부)
- 정책 판정 함수: 유효시간 경과, 재발송 대기 잔여시간, 실패 한도, 일일 한도

**E2E (프로덕션 빌드)** — 세션 관련 버그는 dev에서 재현되지 않는 전례가 있으므로 반드시 프로덕션 빌드로 확인한다.
- 미가입 번호 → 인증 → 온보딩 → 홈
- 기존 번호 → 인증 → 홈 (온보딩 건너뜀)
- 같은 번호로 두 계정이 생기지 않음
- 인증번호 5회 오입력 시 차단, 재발송으로 해제
- 재발송 30초 대기
- 번호 변경 시 이전 인증 상태 초기화
- 카카오 로그인 회귀 없음

## 배포 전 운영 작업

코드만으로는 동작하지 않는다.

1. **Supabase 플랜 확인** — Send SMS Hook 가용 여부. 불가 시 재설계 필요
2. Supabase 대시보드: Phone provider 활성화, Send SMS Hook URL·시크릿 등록, SMS OTP 만료 3분 설정
3. SMS 공급자 계약 및 발신번호 사전등록
4. `supabase/migrations/`에 SQL 추가: `h_profiles.phone` E.164 정규화 + 유니크 인덱스
5. 환경변수 추가: `SMS_PROVIDER`, `SUPABASE_SMS_HOOK_SECRET`, 공급자별 키

DB 마이그레이션은 `supabase/migrations/*.sql`이 source of truth다. `drizzle-kit generate`를 쓰지 않는다.

## 완료조건

티켓에 비어 있어 아래를 제안한다.

1. 미가입 번호로 인증 후 온보딩을 거쳐 홈에 진입한다
2. 기존 번호로 인증 시 온보딩 없이 홈에 진입한다
3. 같은 번호로 두 계정이 생기지 않는다
4. 인증번호가 3분 경과 후 실패하고, 재발송은 30초 대기하며, 번호당 일 5회를 초과하면 차단된다
5. 인증번호를 5회 틀리면 차단되고 재발송으로 해제된다
6. 번호를 바꾸면 이전 인증 상태가 초기화된다
7. 카카오 로그인이 기존과 동일하게 동작한다

**범위 밖 (탈퇴 기능 미구현)**

티켓의 "탈퇴 회원 전화번호 재가입 정책"은 정책만 확정하고 검증은 하지 않는다. 현재 앱에 탈퇴 기능이 없다 — 설정 화면의 "계정 삭제"는 `href: "#"`인 빈 메뉴다.

확정된 정책은 **즉시 재가입 허용, 데이터는 새로 시작**이다. 탈퇴 기능을 구현할 때 다음을 지킨다.

- 탈퇴 시 `auth.users` 행을 삭제한다. `users_phone_key` 유니크 제약이 풀리므로 같은 번호로 즉시 재가입된다.
- 소프트 삭제(`deleted_at`만 표시)를 쓰면 유니크 제약이 남아 재가입이 막힌다. 쓰지 않는다.
- `h_profiles`, `h_user_consents`, `h_user_hobbies` 등 연결 데이터를 함께 지운다.

## 알려진 한계

- **카카오·전화번호 계정 분리**: 같은 사람이 두 계정을 가질 수 있다. 안내 문구로만 예방한다. 계정 통합이 필요해지면 별도 과제로 다룬다.
- **기존 이메일 사용자 7명은 로그인 경로를 잃는다.** 이 중 **클럽 활동이 있는 사용자는 1명**이다 (`jan***`, 클럽 1개). 나머지 6명은 활동 기록이 없는 테스트 계정으로 보인다. 배포 전 이 1명에게 개별 안내가 필요하다 — 전화번호로 재가입하면 기존 클럽 가입 기록은 따라오지 않는다.
- **SMS 비용이 신규 발생한다.** 발송 한도가 곧 비용 상한이다.
